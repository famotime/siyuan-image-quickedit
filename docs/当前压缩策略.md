# 当前压缩策略

本文档描述 `siyuan-image-quickedit` 当前代码中的图片压缩实现逻辑。内容以实际实现为准，对应核心代码位于 `src/services/image-workflow.ts`、`src/services/compression-strategy.ts` 与 `src/services/palette-quantization.ts`。

## 命令目标

当前压缩命令及目标体积比例：

- `compress-75`: 目标为原图大小的 `75%`
- `compress-50`: 目标为原图大小的 `50%`
- `compress-30`: 目标为原图大小的 `30%`
- `compress-10`: 目标为原图大小的 `10%`

目标字节数计算方式：

```text
targetBytes = floor(originalBytes * targetRatio)
```

另有 `convert-webp` 命令，仅执行格式转换，不以目标体积为约束。

## 预处理阶段

执行压缩前，插件会先完成以下步骤：

1. 根据图片块定位目标图片。
2. 读取原图二进制数据。
3. 创建 `ImageBitmap`。
4. 解析原图元数据：
   - 原始宽高
   - 原始大小
   - MIME 类型
   - 文件格式
   - 颜色深度（GIF 固定 8bit，JPEG 固定 24bit，其他格式采样左上角 64×64 区域，含半透明像素判定为 32bit，否则 24bit）
5. 计算图片在文档中的显示缩放比例 `displayScale`。

说明：

- `displayScale` 取显示宽高与原始宽高的较小比值，且不超过 1。
- `displayScale` 仅用于"需要降分辨率时"的起始点。
- 当前逻辑不会一开始就按显示尺寸改分辨率。
- 若原图宽度超过 `1920px`，会先计算自然缩放比例 `naturalScale = 1920 / originalWidth`，后续所有分辨率候选均以此为上限，不再尝试原始分辨率。

## 总体压缩顺序

压缩候选按以下顺序尝试：

1. 若原图宽度超过 1920px，先将起始分辨率上限设为 `naturalScale = 1920 / originalWidth`；否则起始上限为 `1.0`
2. 先尝试起始上限分辨率
3. 如果该分辨率下仍无法达到目标体积，再进入降分辨率阶段
4. 降分辨率阶段从 `min(displayScale, naturalScale)` 开始，并继续递减

每个分辨率下的内部顺序固定为：

1. 先只调整 WebP 质量（全色）
2. 若仍未达到目标，再在该分辨率下依次尝试 5 种调色板压缩

选择规则：

- 不再使用"第一个命中即返回"
- 会收集所有满足 `bytes <= targetBytes` 的候选
- 在所有达标候选中，按观感评分选择最终结果
- 如果所有候选都未命中，返回整个搜索过程中体积最小的结果

## 分辨率尝试策略

候选缩放序列由 `buildCompressionScaleSteps(baseScale, originalWidth?)` 生成。

规则如下：

1. 计算自然缩放比例 `naturalScale`：
   - 若 `originalWidth > 1920`，`naturalScale = 1920 / originalWidth`
   - 否则 `naturalScale = 1`
2. 计算有效基础缩放比例 `effectiveBaseScale = min(baseScale, naturalScale)`
3. 第一个候选始终是 `naturalScale`
4. 第二个候选是 `effectiveBaseScale`
5. 后续依次尝试：
   - `effectiveBaseScale * 0.9`
   - `effectiveBaseScale * 0.8`
   - `effectiveBaseScale * 0.7`
   - `effectiveBaseScale * 0.6`
   - `effectiveBaseScale * 0.5`
   - `effectiveBaseScale * 0.4`
   - `effectiveBaseScale * 0.3`
   - `effectiveBaseScale * 0.2`
6. 每一步都会被限制到 `0.1 ~ 1` 区间
7. 重复值会被去重

例如：

- 若 `displayScale = 0.5`，原图宽度 ≤ 1920px，顺序为：

```text
1, 0.5, 0.45, 0.4, 0.35, 0.3, 0.25, 0.2, 0.15, 0.1
```

- 若 `displayScale = 1`，原图宽度 ≤ 1920px，顺序为：

```text
1, 0.9, 0.8, 0.7, 0.6, 0.5, 0.4, 0.3, 0.2
```

- 若 `displayScale = 1`，原图宽度 = 3840px（`naturalScale = 0.5`），顺序为：

```text
0.5, 0.45, 0.4, 0.35, 0.3, 0.25, 0.2, 0.15, 0.1
```

## WebP 质量搜索策略

每个"分辨率 + 调色板"变体下，采用"智能起点 + 二分逼近 + 局部细化"的方式搜索最优质量。

搜索边界：

```text
最高质量: 0.98
最低质量: 0.05
```

### 智能初始质量猜测

不再固定从 `0.98` 开始尝试，而是根据目标压缩比例估算初始质量：

| 目标比例 | 初始质量 |
|----------|----------|
| ≤ 15%    | 0.3      |
| ≤ 35%    | 0.5      |
| ≤ 55%    | 0.7      |
| > 55%    | 0.85     |

### 搜索流程

1. 先尝试智能猜测质量
2. 若猜测质量已满足 `bytes <= targetBytes`，向上搜索更高质量以尽量提升画质
3. 若猜测质量仍 `bytes > targetBytes`，向下搜索更低质量以达到目标体积
4. 二分逼近，当区间宽度收敛到 `0.02` 以内时停止（安全上限 8 轮）
5. 二分后再做一轮局部细化，在 `[lowerBound, upperBound]` 区间内采样 `25%`、`50%`、`75%` 三个分位点

质量值会被归一化到 `[0.05, 0.98]` 区间内，精度保留三位小数。

### 缓存机制

两层缓存避免重复计算：

- **质量候选缓存**：每个变体内部维护 `Map<number, RuntimeCompressionCandidate>`，避免同一质量值重复编码
- **画布缓存**：同一 `(width, height, maxColors)` 的变体共享已渲染量化的 canvas，避免重复的像素读写和调色板处理。不同质量值仅重新执行 `toBlob()` 编码

这一阶段的特点：

- 不修改颜色数量
- 目标是在当前变体下找到"满足体积约束的最高可用品质"
- 达标后不会立即结束整个压缩流程，而是继续参与最终评分

## 调色板 / 颜色数压缩策略

如果"当前分辨率 + 全色质量搜索"仍达不到目标体积，就在同一分辨率下依次尝试有限调色板版本。

颜色预算顺序为：

```text
256, 128, 64, 32, 16
```

每个颜色预算下，都会再次执行完整的质量搜索流程（高低边界 → 二分 → 局部细化）。

也就是说，同一分辨率下的完整顺序是：

1. 全色 + 质量搜索
2. `256` 色 + 质量搜索
3. `128` 色 + 质量搜索
4. `64` 色 + 质量搜索
5. `32` 色 + 质量搜索
6. `16` 色 + 质量搜索

## 达标候选评分策略

当前实现会对所有达标候选计算一个观感评分，再选择分值最高的结果。

评分函数 `scoreSatisfiedCandidate()` 计算如下：

```text
score = resolutionScore × 0.55
      + paletteScore   × 0.20
      + qualityScore   × 0.20
      + sizeUtilScore  × 0.05
```

各维度的计算方式：

| 维度 | 权重 | 计算公式 | 说明 |
|------|------|----------|------|
| 分辨率保留度 | 55% | `clamp(widthRatio) × clamp(heightRatio)` | 候选宽高与原始宽高的比值之积，各值 clamp 到 [0, 1] |
| 调色板保留度 | 20% | `clamp(log₂(maxColors) / 8)` | 无调色板约束时为 1；256 色 = 1.0，128 色 ≈ 0.875，16 色 = 0.5 |
| 编码质量 | 20% | `clamp(quality)` | 直接使用 WebP 质量参数值 |
| 体积利用率 | 5% | `clamp(bytes / targetBytes)` | 越接近目标体积上限得分越高 |

评分倾向：

- 更高分辨率优先
- 更少的颜色压缩优先
- 更高的 WebP 质量优先
- 在前三项接近时，优先选择更接近目标体积上限的结果

这意味着当前策略追求的是：

> 在满足目标体积前提下，尽量保住分辨率、颜色丰富度和编码质量，而不是尽快找到第一个合格结果。

## 当前量化实现方式

当前的调色板压缩不是复杂的自适应调色板算法，而是基于 RGB 通道位深分配的快速量化：

1. 根据最大颜色数 `maxColors` 计算可用总 bit 数：`totalBits = floor(log₂(maxColors))`
2. 将 bit 数轮流分配给 `R/G/B` 三个通道（先 R，再 G，再 B，循环分配）
3. 将每个通道映射到 `2^bits` 个离散等级，再映射回 0-255 范围
4. Alpha 通道值为 0 的像素完全跳过，不做量化处理
5. Alpha 通道值非 0 的像素，alpha 值保持不变

实现特征：

- 速度快
- 实现简单
- 有损
- 透明像素（alpha=0）不参与量化
- 对视觉质量的控制较粗糙，偏工程化压缩，不是高质量图像量化器

## convert-webp 转换流程

`convert-webp` 命令不以目标体积为约束，而是尝试在不大于原图体积的前提下尽量保留质量。

流程：

1. 若原图宽度超过 1920px，先将输出分辨率降为 `naturalScale` 对应尺寸
2. 依次尝试质量阶梯中的前 4 个值：`0.92, 0.86, 0.78, 0.7`
3. 若某个质量的输出体积 `<=` 原图体积，直接采用
4. 否则在尝试过程中保留体积最小的结果
5. 不做调色板压缩

## 输出格式

当前所有压缩结果统一输出为：

```text
WEBP
```

无论原图是 PNG、JPEG、GIF 还是其他可处理格式，压缩输出都为 `.webp` 文件。

## 进度提示

压缩过程中会输出进度消息。当前主要包括：

- `正在尝试 {width}×{height}`（全色质量搜索）
- `正在尝试 {width}×{height} / {maxColors} 色`（调色板变体）

后续上传和插入阶段的消息由 `kernel.ts` 和 `task-runner.ts` 控制，不在此文档范围内。

## 回退规则

如果没有任何候选能达到目标体积：

- 不报"压缩失败"
- 返回搜索过程中体积最小的那个候选

只有在完全无法生成任何候选结果时，才会抛出错误：

```text
无法生成压缩结果。
```

## 当前限制

当前策略存在以下限制：

- 调色板压缩不是自适应聚类算法，颜色分布利用率有限
- 未使用有损 PNG、AVIF、JPEG XL 等其他格式策略
- 未基于图像内容类型区分照片、插画、截图
- 未针对文字截图做专门锐化或边缘保护
- 未引入 SSIM、PSNR 等视觉质量指标
- 评分仍是启发式规则，尚未引入 SSIM、Butteraugli 等感知指标
- 质量搜索默认假设文件大小随质量参数大体单调变化，极端图像上不一定严格成立

## 当前实现摘要

一句话概括：

> 超宽图先降到 1920px 宽度上限，再根据目标比例智能选择初始质量起点，在当前分辨率下搜索最优质量及调色板；同一变体共享已渲染画布避免重复量化；若仍不够，再逐步降低分辨率并重复搜索。所有达标候选都会参与观感评分，最终选择评分最高的结果；若没有达标候选，则返回体积最小结果。
